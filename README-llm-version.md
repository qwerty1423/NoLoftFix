# NOLoftFix

Reference-profile midcourse lofting for Nuclear Option ARH missiles, implementing
the augmented pursuit guidance approach of **CEAS-GNC-2026-016** (Tahk, Kim,
Jeong & Lee, KAIST, EuroGNC 2026) — expressed in the one variable the game
actually accepts.

## The problem

`ARHSeeker.Seek()` computes its loft bias as

```csharp
float num = Mathf.Min(timeToTarget * timeToTarget * 4.905f * loftAmount,
                      targetDist * loftAmount);
leadVectorWithAccel += num * Vector3.up;
```

with `loftAmount = 0.7` on the AAM-29 Scythe (the prefab overrides the code
default of 0.2). The bias is a function of **time-to-go alone**, and `timeToTarget`
is refreshed at 1 Hz in `SlowChecks()` and then decremented every fixed tick.

Because the bias scales as `t_go²`, it swings wildly with range: below ~45 nmi it
aims *below the launch altitude* and the missile dives; in the 50–65 nmi band it
happens to work; beyond that it over-lofts and arrives with no energy. That is
exactly the reported behaviour. A Python replica of the game's physics using the
**parsed prefab coefficients** reproduces the reported apex altitudes to within a
few percent, including "peak loft 141,000 ft" at 105 nmi (sim: 137,900 ft).

The aimpoint is also recomputed from a PIP that moves on every datalink update,
so there is no persistent trajectory — the missile chases a bias, not a path.

## The fix

Replace the bias with an **offline-optimised reference trajectory** and follow it
by placing the aimpoint on it.

```
xi    = x / X_f                    x = downrange travelled, X_f = launch->PIP
h_ref = sum_k poly_a[k] * xi^k     7th-order polynomial, per the paper
x_ap  = x + lookahead * speed
ap    = launch + dir * x_ap
ap.y  = poly(x_ap / X_f) + trackGain * (h_ref - h_actual)
```

**The paper's APG law `a_com = N·V·(λ_ref − λ)` is deliberately not implemented
literally.** The game has no acceleration-command input: `Missile.Steering()`
does pure pursuit toward an aimpoint and a `PID2D` turns that into body torque.
Pure pursuit toward a lookahead point on a reference path *is* trajectory
following, so that is what this does.

## Two hooks, nothing else

| hook | what it does |
|---|---|
| `ARHSeeker.Initialize` postfix | sets `loftAmount = 0`, which disables the bias in **both** `Seek()` and `SlowChecks()` from one place; captures the launch geometry from `seeker.knownPos`; picks a table cell |

> **`loftAmount = 0` has a side effect that must be compensated for.**
> `ARHSeeker.SlowChecks` computes `targetDist` *inside* its `if (loftAmount > 0f)`
> block, so zeroing the field stops it being written and it sits at `0f`. The game
> then reads it in two places unrelated to lofting — the close-in-under-jamming
> branch (`targetDist < 5000f`, which becomes true at any range) and jink evasion
> (`targetDist > terminalRange`, which becomes never true, killing `ApplyJink`;
> the AAM-29 sets `jinkEvasion.amount = 0.2`). `LoftGuidance.MaintainTargetDist`
> recomputes it every tick from `knownPos`, which is what `SlowChecks` would have
> stored. Guidance itself uses a live slant range and never reads the field.
| `ARHSeeker.Seek` postfix | runs *after* the game's `SetAimpoint()`, so it overwrites the aimpoint with the profile lookahead point |

No transpilers. Both are wrapped in try/catch and the mod disarms itself after 5
failures, degrading to vanilla behaviour rather than to "missiles stop guiding".

```bash
scripts/build.sh --managed-dir "/path/to/NuclearOption_Data/Managed"
scripts/build.sh --managed-dir "..." -c Release     # also makes a .zip
```

Requires the .NET SDK (any recent version; `netstandard2.1` target) and network

## Generating the tables

The tables are **not** included — `Tables/loft_tables.example.json` is a real
3-cell table (30 nmi from 20 000 ft to targets at 1 000 / 10 000 / 20 000 ft)
generated by `grid_dymos.py` from the parsed AAM-29 coefficients. It exists purely
so you can verify the plumbing end to end. Replace it.

**Everything is metric** — km, metres, m/s — in the grid specs, the JSON schema
and the runtime lookup. Tables written before the metric switch still load: the
loader reads the legacy `range_nmi` / `launch_alt_ft` / `launch_kt` /
`target_alt_ft` / `target_kt` keys and converts them.

```bash
cd ../sim
pip install -r requirements.txt
python3 grid_dymos.py --grid grids/scythe-lean.json --jobs 8   # 60 cells, ~20 min
python3 grid_dymos.py --grid grids/scythe.json --status        # see what's left
python3 grid_dymos.py --grid grids/scythe.json --jobs 8        # 252 cells, ~80 min
python3 grid_dymos.py --grid grids/scythe.json --merge --out ../mod/Tables/loft_tables.json
```

Run the lean grid first. It validates the whole pipeline in twenty minutes
before you spend an hour on the full one.

`grid_dymos.py` is crash-resumable: each cell lands in `runs/<name>/cells/` via
write-temp-then-rename, so a cell file is either complete or absent. Re-running
the same command skips finished cells. See `sim/WALKTHROUGH.md`.

Measured ~150 s per cell at 12 nodes, so the 252-cell Scythe grid is roughly
80 minutes on 8 cores. Short-range cells are faster and tend to converge cleanly;
long-range ones often hit the SLSQP iteration limit and still produce a good
trajectory.

## Over-lofting and maneuver authority

The offline objective maximises terminal speed subject to `nload <= gLimit`. That
is an **upper** bound, so a missile with almost no authority satisfies it
trivially and the optimiser will loft into air it cannot turn in. With the AAM-29
curves (`Cl_max` 0.999, `finArea` 0.5, 100 kg dry):

| altitude | game ρ | ρ vs ISA | load available @ 1000 m/s |
|---|---|---|---|
| 25 km (82 000 ft) | 0.0277 | 0.59× | 7.1 g |
| 30 km (98 400 ft) | 0.0049 | 0.20× | 1.3 g |
| 32 km (105 000 ft) | 0.0018 | 0.09× | 0.45 g |
| 35 km+ (115 000 ft+) | 0.000526 | 0.04× | 0.13 g |

`airDensityAltitude` **flattens at 0.000526 above its last key (35 km)**, so past
that the missile has essentially no authority at any speed. This is the failure
CEAS-GNC-2026-016 warns about: *"if the target maneuvers to produce any PIP
change, the trajectory correction of the missile can be a challenging task to
handle at high altitudes."*

Two layers:

- **`min_authority_g`** in `sim/dymos_opt.py` and the grid specs (default 3 g) —
  the proper fix. A path constraint on the load the airframe *could* pull at max
  AoA. Measured on a 110 km shot: apex 34 439 m → **25 496 m**, terminal speed
  797 → 710 m/s. 11% of speed buys back the ability to turn.

Tables generated before the constraint existed should be regenerated. There used to
be a runtime `MaxApexM` ceiling as a stopgap; it was removed because a clamp applied
after the fact distorts a profile the optimiser shaped deliberately, and no measured
failure ever called for it.

## Target motion

The solved profile is an absolute polynomial pinned to the launch and target
altitudes it was generated for, so it cannot be used verbatim once the target
moves. It is decomposed into a **bump** — the polynomial minus the straight line
joining its own two endpoints — which is zero at both ends by construction. The
runtime reference is then rebuilt as

```
h(s) = h_launch + (h_pip_now - h_launch) * s + B(s)
```

so the offline *shape* survives while both endpoints track the live PIP exactly.
The PIP comes from `seeker.knownPos` passed through
`TargetCalc.GetLeadVectorWithAccel(...)` — the same call `ARHSeeker.Seek` uses —
so the lead is preserved rather than aiming behind a crossing target.

Three guards keep that continuous:

1. **`s` is normalised by `xfUsed`**, a first-order lag (`XfLagRateMPerS`) on the
   true launch→PIP distance. Without it, a target turning away grows `X_f`,
   shrinks `s`, and the missile is abruptly told it is earlier in the profile and
   must climb — a step command pure pursuit chases hard.
2. **Progress is `xf0 − remaining range`**, not a projection onto the current
   axis. A projection collapses toward zero if the target turns 90°, which would
   command launch altitude mid-flight.
3. **Cell re-selection cross-fades** (`BumpFadeSeconds`) rather than swapping, so
   picking a different table cell cannot step the reference either.

Verified against the shipped `LoftTable.cs` (`BumpCoeffs`, `Poly.Eval`):

```
B(0) = 0.0000, B(1) = -0.0000                       endpoints vanish
h(0.25/0.5/0.75) rebuilt == original poly to 1e-6   shape preserved
retarget to a moved PIP: h(0), h(1) exact           endpoints follow
10 m target climb -> max reference change 10.0 m    no amplification
```

`pipRefreshes` and `xfDrift` are in the verbose flight log if you want to watch
it work.

## Config

`BepInEx/config/NOLoftFix.cfg`. **Editing it does not need a restart** — the plugin
watches the file and calls `ConfigFile.Reload()`, and every setting below is read
through its `ConfigEntry` rather than snapshotted at load. The three marked
*restart* are the exceptions.

| key | default | meaning |
|---|---|---|
| `Following/LookaheadSeconds` | 3.0 | **the main tuning knob.** Too small and the missile cuts corners; too large and it lags the profile |
| `Following/MaxTrackAngleDeg` | 12 | how far the aimpoint may deviate from the profile slope. Bounds the recovery rate so a slowing missile cannot be commanded into a steeper and steeper dive |
| `Following/TrackGain` | 0.5 | proportional gain on altitude tracking error. 0 = pure lookahead |
| `Following/TargetAltLagRateMPerS` | 250 | how fast the reference endpoint may move. Must stay above the target's own vertical rate |
| `Following/FloorAltM` | 60 | aimpoint is never placed below this. The mod has no terrain query |
| `Lookup/MaxNormalisedDistance` | 0.5 | outside this from any solved cell the mod declines to engage and vanilla lofting stays |
| `General/MinCellTerminalSpeedMs` | 800 | cells predicting a slower arrival are dropped at load. *restart* |
| `General/RejectFlatCells` | true | drop cells that never lofted (apex == launch altitude). *restart* |
| `General/Enabled` | true | master kill switch, checked before patching. *restart* |
| `General/VerboseLogging` | true | the `[flight]` / `[terminal]` / `[law]` lines |
| `Following/FlightLogIntervalS` | 1 | seconds between those lines |
| `Following/DebugDraw` | true | draw the remaining reference profile with a LineRenderer |

Twelve keys, down from twenty-four. The rest were internals nobody had ever changed
(`Neighbours`, `IdwPower`, `MinLookaheadM`, `MaxLookaheadM`, `XfLagRateMPerS`,
`BumpFadeSeconds`, `RebaseWindowSeconds`, `PipChangeThresholdM`) and are now
constants in `Core/LoftSettings.cs`. Two were removed outright: `MaxApexM` (off by
default, unjustified by any observed failure) and the `Relookup*` pair, along with
the cell re-selection code they gated — re-selecting mid-flight steps the profile,
because `BumpCoeffs` pins endpoints and not shape.

## Known limits

- **No terrain awareness.** The aimpoint is clamped to `FloorAltM`, not to the
  ground. Low-level runs need tables generated with terrain in the loop.
- **Terminal phase is untouched.** Inside `terminalRange` (12 000 m) the mod
  returns without overriding, so the game's own radar-locked lead calculation
  runs. This mod is midcourse only.
- **Blending cells with different endpoints.** The polynomials are pinned to
  their own launch/target altitudes, so an inverse-distance blend of two cells
  hits neither exactly. Measured: querying 1 000 m between cells at 305 m and
  3 048 m gives `h(1) = 679 m`. It does not matter much in practice because the
  mod stops overriding inside `terminalRange` (12 km), well before ξ=1, but it is
  why a denser `target_alt_m` axis is worth more than a denser range axis.
- **`target_speed_ms` is carried but not solved.** Reference profiles are generated
  against a fixed PIP, as in the paper. Target motion is handled at runtime — see
  below.
- **Server-authoritative.** Missiles only simulate where `LocalSim` is true, i.e.
  the host. On a dedicated server the mod must be installed *there*, and it is
  unverified whether NO's dedicated server supports BepInEx at all.
- **`converged` is recorded per cell** and is often `false` (SLSQP iteration
  limit). The solutions are still good — they beat the vanilla law by a wide
  margin — but see `sim/WALKTHROUGH.md` §C2 for making them properly converge.
